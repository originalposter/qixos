# Security model
The security model of QixOS outlines what security is and how it is achieved in QixOS.
It describes the assumptions that the model depends on and describes the consequences of those assumptions being wrong.
It goes into the details of the architecture in order to argue that the safety of the system is ensured.

## The QubesOS security model
QixOS piggy-backs heavily on QubesOS for security. The QubesOS security model is a basis for thinking of security in QixOS which modifies it only very lightly and hesitantly.

The Qubes security model is based on virtual machines (VMs) which each is considered its own security zone.
A VM runs whatever software it wants inside of it and depending on that software and the VM configuration, has a higher or lower risk of being 'comproised'.
If the QubesOS security model is sound the compromised VM can only compromise other VMs if those VMs are 'below' it in the 'security hierarchy'.
The 'security hierarchy' in Qubes describes which VMs are 'above', 'below' or 'not related' to each other.
It includes categories such as `AppVM`, `TemplateVM`, `StandaloneVM` and `dom0`
`dom0` is above all other VMs.
A `TemplateVM` is above all `AppVM`s that use it as their template.
`AppVMs` are always not related, even if they share a template, meaning that in a correct Qubes system no `AppVM` can compromise any other `AppVM`.
A `TemplateVM` is not related to any `AppVM` which does not depend on it.
`StandaloneVM`s sit by themselves in the hierarchy not above or below any other VM except `dom0`.
However if they are cloned from a compromise template they will inherit that compromise.

There is a nuance to the above security hierarchy called the qubes remote procedure call system (qrexec).
This allows `dom0` to give special permission for a specified VM to call a specified program in another specified VM, regardless of where these VMs sit in the hierarchy.

It is therefore critical that these policies are constructed with care and that the programs which are opened up are especially hardened to prevent security vulnerabilities.

## The QixOS security model
The QixOS security model leans heavily on the QubesOS security model.
We use the same VM hierarchy system but introduces a couple of new concepts.
We introduce a new special VM `qixos-admin` which sits at the top of its own hierarchy of nix qubes (nubes).
The `qixos-admin` VM is able to create new VMs and it is above every VM it creates.
A VM created by `qixos-admin` will get a QubesOS tag called `created-by-qixos-admin` and this tag lets `qixos-admin` have full control of that VM.

## Invariants
The breaking of any of below invariants is considered a security vulnerability bug in QixOS.

1. `qixos-admin` must not be able to interact with any VM it did not itself create. The one exception to this is `sys-net`. (THIS IS NOT CORRECT, IT CAN INTERACT WITH VMs with `qvm-copy` and the internet. What we mean is that it has no special privilege over any VM except the ones it creates).
2. The compromise of an AppVM does not lead to the compromise of any other VM\*.
3. The compromise of a TemplateVM does not lead to the compromise of any other VM except AppVMs which depended on that TemplateVM after compromise\*.
4. The compromise of a 'inner configuration' does not lead to the compromise of any VM except the AppVM which uses this inner configuration.
5. QixOS does not per default put security vulnerable software on a VM.

\* except if there are non-qixos side channels which can be exploited in the compromised VM. E.g API keys or user configured qrexec policies.

2) is enforced by QubesOS
3) is enforced by QubesOS
4) depends on the assumption that there is no nix build sandbox escape vulnerability. Each template will build the configuration of all of their dependent AppVMs, but these builds happen only inside of a nix build sandbox and as such they can not compromise the template. If a security vuln is found in the build sandbox this would not be true and a compromised inner configuration could compromise the building template and all dependent AppVMs.
5) is hard to guarantee, QixOS tries to ship as little default software as possible and tries to make sure all custom built software is safe of security vulnerabilities.

## Risky surface areas
Anything running in `qixos-admin` is a risky target. `qixos-rebuild` is especially risky since it communicates directly with TemplateVMs through the `qixos.Switch` qrexec command.
`qixos-rebuild` needs to have a write-only policy with regard to `qixos.Switch` with the exception of return error codes and must not trust anything `qixos.Switch` returns.

## Security in QixOS
QixOS is made up of many different virtual machines (VMs).
We consider each VM to be a separate security zone and the security of QixOS is largely about preventing the compromise of one zone to lead to the compromise of another zone.

Compromise of a zone comes from security vulnerabilities, almost always in the form of unintended bugs in the software that runs in that zone.
A heuristic principle that can be used to make systems safer is to run less code in that system, and to try to have the code that does run be highly audited to avoid security vulnerabilities.

In QixOS the way you achieve security is through compartmentalizing your software and your data so that more vulnerable software (e.g browser) does not run in the same security zone as important data (e.g passwords).

## How the system works
There are VMs that through the QubesOS security systems are isolated from each other. We inherit a lot of the Qubes security model and essentially extend it to cover the parts that are new to QixOS.

VMs have various states for how compromised they are. When a VM runs software on some piece of data it is contaminated with the risk of that software+data taking ownership of that VM.
When a VM writes to another VM there is a risk that this write allowed the VM to contaminate that other VM.
Some VMs are able to control over VMs and as such can be said to have a strictly higher security level.

We try in our security model to keep VMs isolated from each other when it is possible.
We try to keep a clear and understandable hierarchy of which VMs control which other VMs. We try to make sure this hierarchy is not inverted.

We try to document all the attack surfaces introduced by QixOS.

## Assumptions
### Qubes security model is not broken
If the QubesOS security model is broken then QixOS makes no guarantees of security.
If for example a xen VM escape vulnerability is used then it is game-over.
